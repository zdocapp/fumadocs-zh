当我第一次看到 [Web Dev Cody 的视频](https://youtu.be/7HUmDAgXI2E?si=CR9fC-f3nysPJJCE) 时，我感到非常惊讶，感觉我终于构建了一些值得一提的东西，而不是另一个被忽视、无人关心的副项目。

到目前为止，我已经在这个项目上工作了大约一年，这对我来说是一段宝贵的经历。这是你在大学里找不到的最好的课程。

## 开源

我收到了很多反馈、问题和疑问。有些直接但粗暴，比如“请修复它，请帮帮我”、“请支持 XXX”。有些则友善且乐于助人，愿意提供 PR。
我感受到了开源的好与坏。

有时，人们因为压力而变得急切和冲动，可能会将他们的挫败感发泄在库的维护者身上。
即使是我自己，也可能受到压力或坏心情的影响。

人们可能希望得到即时答复，维护者会面临诸如“你为什么逃避我的问题？”这样的质问。
我理解一个表现不佳的库可能会浪费你宝贵的时间，但即使我们全力以赴维护这个库，它也不可能完美无缺。

自那以后，我深感自己对开源项目维护者更加尊重了。
至少，在别人的 GitHub 仓库提交 issue 前，我会先检查自己的问题，并尽可能保持尊重 ~~尽管我的语言能力有限~~。

### Issues

我最喜欢的开发者是 [Anthony Shew](https://shew.dev)，我提到他是因为[他提交的 issue](https://github.com/fuma-nama/fumadocs/issues/264) 是我开源生涯中见过最棒的。
他真正关心我对 API 设计的愿景和意见，并提出了非常简洁且具有建设性的功能请求。

显然，我并非完美，也并非经验丰富的库开发者。
Fumadocs 当时无法实现很多功能，如此详尽的功能请求和想法极具力量。他的热情令人鼓舞。

在设置 YAML issue 模板之前，真正遵循 issue 模板的情况非常少，大多数甚至没有提供可复现的仓库或解释说明。

**提交一个规范的 issue，遵循指引，并给维护者一些正面反馈。** 这是你在不花钱的情况下能给维护者的最大动力。

## 文档

编写 Fumadocs 的文档很有趣。最初构建时，我在撰写文档和教程内容方面经验甚少。
通过阅读开发者们的反馈，最常见的问题是找不到某些功能的文档。

我意识到整个文档对初学者来说不够友好，我的朋友们都是资深的 Next.js 开发者，他们当然能轻松理解。
然而，并不是每个开发者都能看懂这份文档。

所以最近我开始重写部分章节，使其对初学者更友好、更有吸引力。欢迎在 Github Discussions 分享您的反馈！

## 什么是 Next？

Web 开发是一个不断发展的行业，但我相信开源精神不会消失。
我不知道未来会构建什么，但这并不重要。
让我们共同构建更好的 Web！
