人们经常问我，我们真的需要一个框架来构建文档站点吗？嗯，**你不需要**。

文档网站在软件开发中非常重要，
公司内部供开发人员理解架构的内部文档，
框架文档，
Web标准文档...

构建文档看似简单，但可能很困难。

构建文档有很多范式，但编写对初学者友好的文档可能很困难。
因此，人们倾向于使用功能强大的文档框架，使文档站点具有交互性且直观易懂。

## 过度工程化

对于小型库/API服务的文档，你可能不需要设置Next.js站点并花费时间编写站点。
在这种情况下，无论是Nextra还是Fumadocs，都无法比GitHub wiki和Swagger文档更好。

它们提供了良好、得体的用户界面，基本功能，以及编写文档的适当工作流程。
开发者体验已经足够好，我想不出有什么理由要切换到一个功能齐全的文档框架，仅仅为了让你的文档看起来花哨。

我只会建议你用markdown编写文档，使其在你的GitHub仓库中可访问。

## 为什么需要框架？

现在你可能想知道，为什么主要服务和框架都有自己用文档框架构建的文档站点？

当然，*通常*使用像 GitHub Wiki 这样的工具就足够了，但这并非总是如此。
以组件库为例，你无法用 Markdown 来展示你的组件。
你会不断发现普通的 Markdown 文档缺乏能力和灵活性。

文档框架旨在解决这个问题，它们能够与主流库如 **React.js** 和 **Vue.js** 集成。
优秀的例子包括 Vitepress、Mintlify 和 Nextra——它们让编写文档更加便捷高效，同时为读者提供了更好、更专注的体验。

对于任何超出简单库或 API 服务的项目，**值得一试。**

### 重新发明轮子

我绝不建议在没有合适的文档框架的情况下，自行构建“自定义文档站点”。
尽管有 **不要重新发明轮子** 的原则，但手工制作的文档站点实际上需要付出更多努力才能使其像样。

1. 文档搜索
2. 用户友好的导航体验
3. 阅读体验
4. UI/UX 设计

正确实现这些功能听起来就已经令人头疼了，对吧？

文档本身绝对不是你的首要任务。你不应该把宝贵的时间花在重新发明轮子上——**这不值得**。

在我看来，我宁愿使用 GitHub Wiki 也不愿重新发明轮子。
为什么不选择一个像样的解决方案呢？它节省了你宝贵的时间，并有助于减少互联网上糟糕的文档站点。

## Fumadocs 关注什么？

我个人更看重阅读体验，而非花哨夺目的用户界面。
您可能会注意到，我们并未处处使用动画，也避免了许多浮华的设计。

界面的华丽应仅停留在着陆页，文档站点应专注于**内容**。
导航元素是浏览站点的辅助工具，绝不应在屏幕上占据过多空间。

我最讨厌的设计莫过于*双侧边栏*，它既令人困惑又毫无意义。
您完全可以将所有项目组织到一个简洁的单一边栏中，但人们却选择在导航栏添加两个汉堡按钮。

## 结论

1. 对于小型库，您不需要功能全面的文档框架
2. 不要自行构建文档站点，请使用合适的文档框架
3. Fumadocs 专注于阅读体验
4. 您也应专注于内容
