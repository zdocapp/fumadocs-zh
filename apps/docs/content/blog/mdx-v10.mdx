## 问题所在

Fumadocs MDX 在文档处理方面表现优异，但我们同样希望优先考虑灵活性和代码组织。

此前，它只是一个简单的 Webpack 加载器，将 **MDX** 转换为 **JavaScript**。
您将 MDX 处理器选项传递给加载器，它会将这些选项转换为 JavaScript 文件。
然后，会导出一个 `.map.ts` 文件：

```ts
export const map = {
  'docs/index.mdx': import('./docs/index.mdx'),
  'docs/guide.mdx': import('./docs/guide.mdx'),
};
```

您的 Next.js 应用将导入该映射文件，并访问可用的 MDX 文件。

这种模式是可行的，但我们开始发现一些问题：

- **缺乏内置方式定义多个集合：**

  例如，我们有一个用于博客文章的目录和一个用于文档页面的目录。

  在 Fumadocs MDX 中，所有这些资源都会被转换为由 `.map.ts` 导出的单一对象：

  ```ts
  export const map = {
    'blog/post.mdx': import('./blog/post.mdx'),
    'docs/index.mdx': import('./docs/index.mdx'),
  };
  ```

  我们使用 Source API 的 `rootDir` 选项实现了一个解决方案，但这并非理想方式。
  这也给我们带来了另一个问题：

- **每个集合需要不同的 MDX 选项：**

  同上例，我们有一个用于博客文章的 `/blog` 目录。
  如果我们想要添加一个**仅对博客文章生效**的 remark 插件，这在 Fumadocs MDX 中是无法实现的。

  一旦应用了 remark 插件，它将对所有 MDX 文件生效，包括文档目录中的 MDX 文件。

- **Turbopack 兼容性：**

  Turbopack 不允许向加载器传递不可序列化的选项。
  然而，整个 MDX、remark 和 rehype 生态系统都使用函数作为插件。
  函数是不可序列化的，除非我们找到支持 Turbopack 的无缝解决方案，否则无法将 Fumadocs 迁移到 Turbopack。

- **编译时验证：**

  所有模式验证都无法在构建时完成，因为 MDX 加载器实际上*并不知道你在 `source.ts` 中定义的集合*。

  此外，Zod 模式是在 `source.ts` 中传递给源适配器，而不是传递给加载器：

  ```ts
  import { loader } from 'fumadocs-core/source';
  import { createMDXSource } from 'fumadocs-mdx';

  export const source = loader({
    source: createMDXSource(map, {
      // 模式
    }),
  });
  ```

  这失去了一些可能在打包器层面完成的性能优化。

- **无类型：**

  从 `.map.ts` 文件导出的 `map` 对象类型为 `unknown`，只有在与 Source API 的 `loader` 一起使用时才会被类型化。

  这避免了自动生成类型的复杂性，但我希望使其具有类型，并且无需 Source API 即可使用。

### 解决方案

参考 Content Collections 和 [Velite](https://velite.js.org) 的设计思路，我认为为 Fumadocs MDX 提供一个配置文件会非常理想。

#### `source.config.ts`

我们可以让语法与 Content Collections 及其他工具相似，以降低采用门槛。
定义一个集合：

```ts
import { z } from 'zod';

export const blog = defineCollections({
  dir: './blog',
  schema: z.object({
    // the schema
  }),
  mdxOptions: {
    // remark plugins?
  },
});
```

MDX 加载器读取配置文件，找到文件对应的集合，进行验证，并使用集合中的选项进行编译。

这使我们能够正常传递 MDX 选项，同时不违反 Turbopack 的规则。

### 实现方式

由于配置文件是用 TypeScript 编写的，我们需要一个打包器来读取它。
我使用了 esbuild，这是一个用 Go 编写的高性能打包器。

打包配置文件后，动态导入将按预期工作。

```js
await import('./source.compiled.mjs');
```

#### `.map` 文件

我们需要一个地方来导入编译后的集合。
之前，我们简单地使用 Webpack 插件生成了一个 `.map.ts` 文件。
它声明了类型，但不包含实际数据。

```ts
export declare const map: unknown;
```

将使用一个加载器将 `.map.ts` 文件转换为上述输出：

```ts
export const map = {
  'docs/index.mdx': import('./docs/index.mdx'),
  'docs/guide.mdx': import('./docs/guide.mdx'),
};
```

生成的 `.map.ts` 文件永远不会改变，因为它不依赖于配置文件。
无论你如何配置，都只会导出一个类型为 `unknown` 的 `map` 对象。

现在，我们需要为每个集合生成类型，并且这些类型可能会随着集合的更改而变化。
之前的方法不再适用。

我将 `.map.ts` 文件重命名为 `.source/index`，`index.d.ts` 和 `index.js` 均由 Fumadocs MDX 生成，而非使用加载器。

已实现映射文件生成器，它会读取配置文件并根据导出的集合生成输出。

#### 自动重载

我们需要监听变更：

- 当输入文件被添加/删除时，在 `.source/index.js` 文件中添加或移除相关条目。
- 当配置文件变更时，重新编译受影响的文件，并更新 `.source/index.d.ts` 中的生成类型。

我选择使用 chokidar 来监听文件变更，效果良好。
文件监听器位于 `next.config.mjs`，独立于 MDX 加载器。

为了在配置文件变更时通知打包器，我们添加了**哈希值**。

```ts
export const collection1 = [import('./docs/index.mdx?hash=hashOfConfigFile')];
```

当配置哈希值变更时，文件将被重新编译。

为优化性能，我们还添加了集合名称。

```ts
export const collection1 = [
  import('./docs/index.mdx?hash=hashOfConfigFile&collection=collection1'),
];
```

加载器从资源查询中获取输入文件的集合，无需额外步骤检测其关联的集合。

### 结果

将生成一个 `.source/index` 文件，该文件具备完整类型支持。
当您修改配置文件时，文件将被重新编译。

- 支持 Turbopack，我们在代码库中提供了使用 Turbopack 的小型示例。
- 多集合支持，每个集合拥有独立的 MDX 选项。
- 运行时 + 构建时验证与转换。
