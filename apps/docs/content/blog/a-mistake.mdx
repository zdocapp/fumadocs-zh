## 一个失误

Fumadocs 的早期失误在于 **Fumadocs CLI 推出过晚且在文档中提及不足**。

为了进一步推进 CLI 方法，例如最近对 Shadcn CLI 的支持，我们必须做出一些改变。
如果早期采用者的自定义超出了我们抽象层能够缓解的范围，他们将面临问题。

**例如：** 一个小的 CSS 变更仍可能破坏临时的 CSS 自定义，我们只能确保通过 CSS 选择器限定范围或公开选项的向后兼容性：

```css
#nd-sidebar {
  /* this will work forever */
  background-color: red;
}
```

为了让 CLI 更好地工作，我们需要布局组件完全独立以实现模块化。理想状态是：

- 普通用户可以使用公开选项，享受上游的 UI 迭代。
- 高级自定义可以使用 Fumadocs CLI，避免上游变更。

这与[这篇关于 UI 自定义的文章](/blog/customise-ui#the-solution)中描述的解决方案相同。

### 一个良好示例

对于像 nuqs 所做的较轻量自定义，通过 PR 从旧版本迁移 [#1056](https://github.com/47ng/nuqs/pull/1056) 可以减少用户端的代码量，且迁移过程简单。

### 问题所在

当你的临时方案更复杂时，结合代码库的技术债务，迁移会困难得多。

我观察到的一些问题：

#### 页面树 API 被忽视的问题

页面树实际上是 Fumadocs 的核心概念，统一了文档的所有导航和链接。

即使在早期版本中，它已经是一个支持根文件夹等功能（自 v12 起）的强大 API：

<div className="flex flex-row justify-center mx-auto max-w-[300px]">
  ![Preview](/blog/v12-root-toggle.png)
</div>

一些项目既不依赖我们的基于文件的路由，也不使用页面树 API，这导致在侧边栏和 `loader()` 方面出现了大量临时解决方案。

其理念很简单：

```txt tab="Server"
files -> Fumadocs -> page tree
```

```txt tab="Client"
page tree -> navigation components (e.g. page footer & sidebar)
```

正确使用它已经可以大幅减少工作量，我们为硬编码页面树提供了[页面树规范](/docs/headless/page-tree)。

#### CSS 变量被忽视的问题

Fumadocs 从一开始就使用 CSS 变量来处理所有颜色，其命名与 Shadcn UI 完全相同，这使得自定义变得容易。

但我注意到有些人覆盖的是 Tailwind CSS **类**而不是**颜色**，例如：

```css
#nd-sidebar .color-fd-background\/80 {
  color: red;
}
```

实际上我们一直支持更简单的方法：

```css
#nd-sidebar {
  --color-fd-foreground: red;
}
```

现在我们还有一个 Shadcn UI 预设，可以重用主应用程序中的颜色。

### 早期反思

我认为 CLI 方法是正确的，它将成为高级自定义的主要方式。

我的未来计划：

- **持续改进 Fumadocs CLI：** 新增安装时优化功能，根据您的选项移除未使用的文件（例如使用现有的侧边栏组件而非安装新组件）。
- **更优的版本管理策略：** 减少抽象层级以缓解上游变更影响，改为直接对组件进行版本控制（例如创建新的 `fumadocs-ui/layouts/v2/page` 而非进行重大的 UI 改动）。
- **增加 Fumadocs 原生云功能：** 提供更多官方集成方案，例如专为 Fumadocs 设计的监控/分析功能。

我最大的目标是组建自己的开发团队或初创公司，我意识到自己的时间过于有限，无法实现理想中的卓越软件。
存在许多我始终无暇打磨的粗糙边缘，以及待办事项过多——即便人工智能已处理了基础工作。
